# GitHub Issue / PR

Issue・PR を作成・更新するときに読む。本文の詳しさは変更の規模に合わせ、分類と確認は省略しない。

## 必須の管理項目

- **Issue・PR ともにラベルを必ず付ける。** リポジトリの既存の分類を使い、種別と該当する領域ラベルを付ける。対応する規約がなければ、不具合は `bug`、機能追加は `enhancement`、その他の作業は `task` を基準にする。必要なラベルが無い場合はリポジトリの規約に従い、分類体系を勝手に増やさない。既存の適切なラベルは残す。
- Issue は **Issue Type・Priority・Effort** も設定する。Type とラベルは別の項目。Bug は不具合、Feature は要望、Task は実装・調査などの作業とし、リポジトリの定義を優先する。
- Priority は影響と緊急度、Effort は調査・実装・検証を含む作業量から判断する。既存の尺度を使い、見積もりの根拠を短く残す。
- 作成・更新後は再取得し、Issue の Type・ラベル・Priority・Effort、PR のラベルを確認する。未設定・権限不足・機能未提供は項目と理由を報告し、設定済みと扱わない。属性操作の詳細が必要な場合は [issue-fields.md](issue-fields.md)。

## Issue

Issue は、何が問題で、どう直し、何をもって完了するかを判断できる計画にする。目的・背景・完了条件を残し、後で読んでも判断を引き継げるようにする。

不具合の Issue には次を含める。既存テンプレートへ収め、小さい修正は簡潔に書く。

- **内容と根拠**：期待する挙動・実際の挙動、再現手順と条件、確認した版や環境、関連コード・試験・ログ。コードから確定できた欠陥と、実環境で発生を確認した事象を区別する。原因の仮説や未確認事項はその旨を書く。
- **修正の方向性**：推奨する修正と理由、変更する責務・守る契約、主要な代案と採らない理由。未決の判断がある場合は、決めるための調査と相手を明示する。未決を隠して実装可能と扱わない。
- **影響範囲**：影響する利用者・機能・呼び出し元・データ・外部連携、互換性や移行、想定される回帰。分からない範囲は未確認と書く。
- **重要度と優先度**：被害の大きさ・発生条件や頻度・回避策・緊急性を根拠にする。被害の重大さと着手順を分け、Priority は既存の尺度へ対応させる。
- **工数の見積もり**：調査・実装・検証の作業量、前提と不確実性。必要なら人時・人日などの幅を示して Effort へ対応させる。待ち時間や依存先の作業と、自分が行う作業量を混同しない。精度が出ない場合は調査分を見積もり、残りの再見積もり条件を書く。
- **実装計画と完了条件**：必要な作業、依存・実行順、修正を確かめる試験や操作、関連 Issue・PR。実装中の発見で方針・範囲・見積もりが変わったら、本文の計画を更新する。

### 結合・分解と計画の整理

同じ原因・同じ完了条件の重複は既存の主 Issue へ集約する。似た症状だけで同一の不具合と判断せず、独立して修正・検証できる課題は分ける。大きな課題は、独立して検証・提供できる単位へ分け、依存関係・担当範囲・順序を示す。小さな変更に別の計画用 Issue を強制しない。

結合・分解前に、各 Issue の固有の再現条件・根拠・完了条件・未完作業・関連 PR を照合する。移動先へ情報を残し、親子・重複元と集約先を相互に辿れるようにする。担当者や人の決定を勝手に置き換えず、進行中の作業と調整する。

close は依頼された整理の範囲で行う。重複は集約先と理由を残し、未修正を修正済みと表さない。分解元に追跡の役割がある場合は親として残し、子を作っただけで完了にしない。無関係な Issue の一括 close・削除は含めない。更新後は本文・状態・関連付けを再取得し、固有の条件が落ちていないことを確認する。

## PR

PR は、実際の差分と検証で Issue の計画をどう満たしたかを示す。何がどう変わるかと理由、関連 Issue、実際の検証結果を書く。Issue の完了条件をすべて満たす場合に `closes #N` を使い、一部の実装・調査・参照は通常のリンクで残す。子課題の PR で未完の親まで閉じない。Issue のない変更に架空の関連付けを作らない。

試験・ビルド・操作確認は実施結果と未確認を分けて記録する。利用者への影響・制約・移行があれば添える。実装結果の理解に必要な説明へ絞り、Issue の計画を複製しない。

作成・更新・マージ前に [PR レーン](../../../review/references/pr-lanes.md) を読み、対象製品の方針に従って分類する。レーンのラベルは種別・領域ラベルに追加する。確認が必要な理由と、共有だけでよい話題を分ける。

## 書式

対象リポジトリの指示と `.github/` の既存テンプレートを優先する。雛形がなければ上の情報を簡潔にまとめ、見出しや順序は内容に合わせる。Issue・PR 作成の副作用としてテンプレートを追加・改変しない。

タイトルは何を解決・変更するかが分かる要約にする。外部の根拠があるときは本文へ出典リンクを残す。

## Assignment

報告・読み取り専用の調査では担当を付けず、実装に着手する前に認証ユーザーを追加する。既存担当者を削除・置換せず、他人が担当中なら共同担当の合意を確認する。close 済みには追加しない。設定後は再取得し、失敗時は状況を報告する。

## ブランチ命名

対象リポジトリの規約を優先する。規約がなければ Issue の実装は `{issue番号}-{自然な英文}`（例: `42-fix-pagination-offset`）。
