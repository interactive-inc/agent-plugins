# CHANGELOG

リポジトリ直下の `CHANGELOG.md` に、価値のある変更だけを記録する。PR を出すときに書き足す。

生成コマンドは作らない。何を書くかは意味の判断なので、機械生成すると全マージが並んで読めなくなる。書かない判断ができることがこの運用の本体。

## 書くかどうかの判断

「利用者から見て意味があるか」「開発者が知る必要があるか」のどちらかを満たすなら書く。

書くもの。

- 利用者の操作・画面・データに影響する追加と変更
- 不具合の修正。特に、利用者が気づかないまま損失につながっていたもの
- 権限・認可の変更。誰が何をできるかが変わるもの
- 運用手順が変わるもの

書かないもの。

- 内部整理、リファクタ、命名変更、ファイル移動
- 未使用コードの削除、規約揃え、型注釈の追加
- テストの追加・修正だけの変更
- 依存の更新

迷ったら書かない。CHANGELOG が内部作業で埋まると誰も読まなくなり、書く習慣ごと失われる。

## 書式

```markdown
# CHANGELOG

（何を書き、何を書かないかの 1 段落）

## YYYY-MM-DD

### 追加

- 変更内容を利用者に分かる言葉で 1 行（#Issue番号）

### 変更

### 修正
```

日付は開発者のタイムゾーン。新しいものを上へ積む。節は「追加」「変更」「修正」で分け、該当が無い節は書かない。

根拠には Issue 番号を添える。PR 番号ではなく Issue 番号を使う。何を解決したかが辿れるため。

不具合の修正では、それが起きるとどうなるかを一言添える。影響が書いてあると後から読んで判断できる。

## リリースとの関係

main へのマージが即デプロイになる構成では、技術的にはマージ＝リリース済みだが、利用者向けの意味では成立しない。1 日に何度もマージされるうえ、内部整理が大半を占めるため。

CHANGELOG は毎 PR で追記してよい。利用者向けの案内は、伝える価値のある変更が溜まったときに不定期で出す。CHANGELOG がその素材になる。

利用者向けを日付で定期化しない。溜まっていない週に無理に出すと中身が薄くなり、読まれなくなる。
