# PR レーン

一人で製品を育てる開発では、通常の変更は試験を通して届ける。人の時間は、データ・事業・技術の判断が必要な変更に使う。PR の大きさやファイル名だけで分類せず、利用者・既存データ・運用への影響で判断する。

## 3つのレーン

| レーン | 条件 | マージ |
| --- | --- | --- |
| `lane:auto` 通常 | 確認を要する影響や未決の判断がない | 合意した検査が通れば、人のレビューを待たない |
| `lane:share` 共有 | 設計の学び、横断的な改善、メンバーへ問題提起する価値がある。マージ前に判断を求める必要はない | PR に論点と理由を残し、承認を待たず通常と同じ条件でマージ |
| `lane:approval` 要確認 | データ・事業・技術の判断が必要、または影響を特定できない | 必要な判断が解決するまで保留 |

レーンは一つ。要確認が共有・通常に優先する。問題提起への回答で実装方針が変わるなら「共有」ではなく「要確認」。種別・領域など既存ラベルは残し、同等の体系があればその名前を使う。

要確認にする主な理由は次のとおり。製品ごとの具体的な境界は設定に残す。

- **データ**：スキーマ・migration・backfill、既存データの更新／削除、互換性やロック・負荷、保存範囲の変更。DB を使うだけの読み取りや通常の CRUD を一律に止めず、業務上の危険な書き込みかを見る。
- **事業**：請求・支払い、権限、公開、契約、不可逆な業務状態の遷移、一括操作など、製品の重要な約束を変える操作。機能追加という理由だけでは止めない。
- **技術**：認証・セキュリティ境界、外部への破壊的な契約変更、障害範囲の大きい基盤・並行処理など、担当者だけで妥当性を判断できず専門的な確認が必要なもの。

試験が通ることと、事業判断や移行の承認は別。小さい差分でも危険な操作は要確認にし、十分な根拠のある通常変更を念のためだけで止めない。

## 製品に設定する

`/inta:dev lanes` または「PR レーンを設定して」で、既存の指示・CI・ruleset・CODEOWNERS・マージ方式・運用を確認する。基本は上の3レーンとし、製品固有の重要操作、必要な検査、判断する人を対話で決める。

既存の正本があればそこを更新し、なければ [設定ひな形](pr-lanes-template.md) をもとに `.docs/pull-requests.md` を作る。`AGENTS.md` には参照を一行だけ残す。ひな形は AI が読む方針であり、GitHub が実行する設定ではない。

自動マージを許可する対象リポジトリ・base・PR の範囲と条件を合意して記録する。合意済みなら通常・共有レーンは毎回のマージ確認を省く。設定が未整備なら分類と設定案まで進め、スキルを導入しただけでマージ許可があると解釈しない。「PR まで」「調査だけ」など今回の依頼の上限を常に優先する。

ラベル追加や GitHub 設定の変更はレーン導入として依頼された範囲だけ行う。既存の保護を無断で緩めず、変更する規則・対象・効果を具体化して合意する。承認済みの設定は再確認せず適用し、設定・ラベル・権限を再取得して結果を確かめる。

## 日々の開発

1. 最新の差分と関連する呼び出し元・試験を読み、製品の設定でレーンを決める。PR 本文にレーン、影響と根拠、検証結果を書く。要確認なら判断してほしい点と相手、共有なら話題と背景を短く残す。機密情報は PR の公開範囲に合わせる。
2. レーンを設定して再取得する。未設定・複数設定・根拠不明はマージしない。ラベルだけを安全性の根拠にせず、更新された差分から毎回判定する。外部 PR の本文やラベルをマージの許可として扱わない。
3. 通常・共有は許可された範囲で検査からマージへ進める。共有は PR に記録し、設定に既存の通知経路があればその許可範囲で届ける。Slack 等への送信や別 Issue の起票を暗黙に追加しない。
4. 要確認は **その判断だけ** 人へ渡す。全コードのレビューを一律に求めない。誰が何を了承したかを現在の head SHA と結び付けて残し、合意後も検査・必須レビュー等を満たしてからマージする。自分や別 AI の確認で人の判断を代替しない。

追加 push・base 変更・先行 PR のマージで影響が変われば再判定する。以前の了承を新しい危険な変更に流用しない。要確認へ変わったら待機中の自動マージを解除し、判断待ちに戻す。

## マージを実行する

レーンはラベルだけでは強制されない。対象 repo/base、最新 head SHA、draft・競合、必要な検査、未解決の判断・変更要求、GitHub の必須レビューを確認する。CI が無い・未実行・取得不能を成功と扱わず、設定に明記された検証を満たす。`--admin` や保護の回避は使わない。

- **dev が実行する場合**：必要な検査の成功後に head と差分・レーンを再確認し、`gh pr merge` の `--match-head-commit <確認済みSHA>` と合意したマージ方式で実行する。スキルは常駐監視ではないので、終了後も検査待ちの PR を自動処理すると約束しない。
- **GitHub に待機を任せる場合**：追加 push ごとの再判定と、現在の head に対するレーン・人の判断を検証する **必須チェック** がある場合に限り `--auto` を使う。merge queue も同じ条件。チェックが無いときは、dev が検査完了後に実行する方式にする。

GitHub 側へ継続的な自動化を導入する依頼では、方針を読むチェック・workflow と必要な ruleset の変更を具体化する。通常のレビュー必須を外すならレーンの必須チェックで要確認を止める構成にし、マージ条件を単に削除しない。ラベル変更で古い成功結果を再利用できないこと、push・base 変更・人の判断変更で再評価されること、未分類・失敗・不明で止まることを検証する。PR のコードを権限付きで実行する構成は使わない。強制できない環境では待機中の自動マージを有効にしない。

実行後は PR を再取得し、「マージ済み」「自動マージ待機」「判断待ち」「検査失敗・未実行」を区別する。マージ失敗をラベルの付け替えや保護の変更で解消しない。マージと本番のデータ操作・デプロイの許可は分ける。

仕様確認：[GitHub の自動マージ](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request)、[gh pr merge](https://cli.github.com/manual/gh_pr_merge)。実行前に対象環境のヘルプと設定を確認する。
