# 値と状態の表現

必要な不変条件を、最も単純に表せる形を選ぶ。パターン名や件数を理由にクラス・層・ファイルを増やさない。

## 値

単純な入力検証は既存のスキーマを使う。検証と業務上の振る舞いを一緒に保つ必要がある値は [Value Object](value-object.md) にする。更新は元の値を壊さず、新しい値を返す。Fluent API は操作の意図が読みやすくなる場合だけ使う。

同じ構造の ID・通貨・単位を混同する危険がある場合は branded type や Phantom Type を検討する。型パラメータを付けただけで区別できると思い込まず、混同するコードが型検査で拒否されることを確かめる。

## 状態遷移

- 単純な状態は通常の値と関数で表す。
- 複数の入力で UI 状態が変わる場合は、純粋な Reducer と判別 union の Action を使う。通信などの副作用は外で行う。
- 許可される順序が業務要件なら、状態と遷移を明示する。状態ごとにデータや操作が大きく違う場合はクラス分割、共通データで操作だけが違う場合は型による制約も選べる。

開始・成功・失敗・再試行の状態を試験する。コンパイル時の制約で、外部入力の実行時検証を代替しない。
