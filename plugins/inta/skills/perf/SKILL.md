# perf

既存のコードに性能改善の視点を当て、当てはまる箇所を見つけて直す。説明用の架空例は [cases.md](references/cases.md) にある。実際の製品の計測値や履歴は含めない。

成果物は差分である。視点の一覧や「確認してください」のメモを人に渡さない。候補は機械的に集め、本物かどうかは自分で確かめ、本物なら直して同値を示す。人に返すのは、直した結果と、判断が要る少数の提案だけにする。

## 前提となる式

```text
応答時間 ≒ 直列に待つ DB 往復の段数 × 1 往復の待ち
          ＋ 読む行数（DB の実行時間とコスト）
          ＋ 計算（CPU）と転送量
          ＋ 初回起動（モジュール評価・バンドル）
画面の待ち ≒ 最初に描けるまでに直列で待つ要求の連鎖
```

サーバレスとリモート DB の構成では、SQL自体が短時間でも、計算とDBの距離によって往復の待ちが大きくなる。効くのは「遅い SQL を探す」より、段数・読み行数・取得量を減らすことである。

## 範囲の決め方

- 引数でパス・画面・API が指定されたら、そこから辿れるコード（画面なら呼ぶ API とそのハンドラ）を範囲にする
- `diff` や「この変更」と言われたら、現在の差分に含まれるファイルと、差分が呼ぶ読み取りを範囲にする
- 指定が無ければ、次の順に当たる
  - 本番の統計が読めるなら、読み行数の合計と回数が多いクエリ、wall の長い経路から（読み方は [cloudflare-d1.md](references/cloudflare-d1.md)）
  - 読めなければ、全 API 共通の前段（認証・権限・テナント解決）→ ホーム・一覧など全員が開く画面の API → スキャナの候補

## 進め方

1. 候補を集める。範囲に `scripts/find-candidates.sh <パス...>` を実行し、視点ごとの候補を得る。リポジトリ全体に流すと視点によっては数百件になるので、確定に回すのは絞った範囲の出力にし、全体の出力（await の多いファイル、件数の多い視点）は範囲の優先順位を決めるのに使う。スキャナが拾えない視点（前段・重複・不要計算・再構築）は、[checks.md](references/checks.md) の見つけ方に従い、段数カウンタ（[verify.md](references/verify.md)）や本番の統計で探す
2. 候補を確定する。候補ごとにコードを読み、[checks.md](references/checks.md) の「確定の条件」で判定する。根拠（EXPLAIN、読み行数、段数、呼び出し側が読むフィールド）を取る。誤検知は捨て、件数だけ数えておく。範囲が画面や API 数本に絞れているときは、スキャナの候補に無くても範囲内の DB 読み取りすべての EXPLAIN を取る。索引の無い列で範囲を絞る全走査は、字句ではなく計画にしか現れない
3. 優先順位を付ける。影響範囲（全 API 共通 ＞ 全員が開く画面 ＞ 一部の画面）× 量（読み行数・段数・CPU）の大きいものから直す。候補が多いときは、上から順に進めて残りの件数を報告する
4. 同値を固定してから直す。変更前の結果を固定するテストが無ければ先に足し、緑を確かめてから [checks.md](references/checks.md) の直し方で直す。1 つの視点 × 1 つの経路を 1 つのコミットにすると、効果と退行を切り分けられる。コミットしない依頼なら、差分のどの範囲（`path:line`）がどの視点かを報告で分ける
5. 検証する。同値の証明（結果の一致、権限の境界）、退行の固定（段数・本数・読み行数の上限テスト）、対象リポジトリが定める format / lint / typecheck / テスト。画面に関わる変更は実ブラウザで確かめる（[verify.md](references/verify.md)）。表示速度（Web Vitals）を同じ条件で測るときは [inta:test](../test/SKILL.md) の `perf` を使う
6. 報告する。下の「報告」の形で返す

## 直すものと、直さず判断を仰ぐもの

直してよいのは、成功時の応答・帳票・権限の結果を変えず、それをテストで示せる変更である。失敗経路だけが変わる場合（読まなくなった処理の例外で 500 にならなくなる等）は、意図した差として報告に書く。前段・段数・行ごと（N+1）・重複・不要計算・派生表・述語・相関・全件・bind・取得量（既存の形を残した追加）・再構築・連鎖・境界・入口・配信資産・無効化がこれに当たる。

次は根拠が揃ったときだけ直し、揃わなければ提案に留める。

- 索引の追加。本番と同じデータ量で、同じ表を読む他のクエリの計画を前後比較できたときだけ足す。本番を見られない依頼では足さず、影響するクエリの列挙（部分索引なら述語で検索）と、合成データでの前後比較を根拠に付けて提案に回す
- 述語の書き換えで結果集合が変わりうるもの（`LIKE` → `GLOB` で値に記号が含まれうる等）。本番で新旧の結果を比べられたときだけ直す
- 計画が DB の統計の有無で逆転する変更。本番に統計があるかを確かめ、どちらの状態でも悪化しないときだけ直す。恒真の条件を足してプランナに索引を選ばせるような誘導は、統計が入ると逆効果になりうるので提案に回し、構造的な直し（部分索引など）を推す（[checks.md](references/checks.md) の「索引」）

次は直さず、根拠と推奨案を 1 つ付けて判断を仰ぐ（[checks.md](references/checks.md) の末尾）。

- 計算と DB の配置の変更（距離）
- 集計結果のキャッシュの導入
- 権限を署名済みトークンへ載せて前段の DB 読み取りを省く変更
- 起動時の表示用トークンのような、認証の仕組みを足す変更
- 既存 API の応答から項目を削る変更
- 共有モジュールの公開境界の変更（複数の製品で同一に保つコード、多数の呼び出し元を持つ集計関数など）。範囲の外へ波及するため、必要な入力の追加などを推奨案として示す

## 守ること

- 対象リポジトリの規約（ブランチ、コミット、migration、テストランナー、dev server、スクリーンショットの扱い）に従う。push と PR は依頼されたときだけ行う
- 本番 DB には読み取り専用の SELECT / EXPLAIN だけを流す。DDL やデータの変更は migration と deploy の経路で行う
- 計測のために足すヘッダ・ログ・トレースに、個人情報・token・SQL の bind 値を載せない
- 権限・失効の確認を、速さのために省かない。画面用の表示情報を認可の根拠にしない
- ローカルの小さな DB では、往復の待ちも、本番規模の実行計画も、bind やメモリの上限も再現しない。ローカルの ms ではなく、段数・本数・読み行数・計画で比べる

## 報告

人に読ませるのは結果だけにする。視点ごとの確認結果を並べない。

- 直したもの: 1 件ごとに、視点、場所（`path:line`）、根拠（変更前の読み行数・段数・CPU・EXPLAIN）、変えたこと、同値の証明、変更後の値、コミット
- 判断を仰ぐもの: 根拠と推奨案を 1 つ。無ければ書かない
- 直さなかった候補: 視点ごとの件数と、主な理由（誤検知・小さな固定のマスタ・効果が計測で小さい等）を 1 行ずつ
- 確かめられなかったこと: 本番の統計を読めなかった、本番相当のデータで計画を比べられなかった等と、その結果どの候補を保留したか

数字は条件とセットで書く。ローカルの段数や SQL 単体の読み行数を、画面の速さの改善として書かない。配信後に同じ条件で測り直すまでは「配信前の値」と明記する。
