# 構造とテスト容易性

責務と試験の境界を明確にし、変更箇所を小さく保つための方法論。表記だけを固定する [preferences](../preferences/index.md) とは分けて保守する。

- 実装は **1ファイル1関数または1クラス**。ファイル名は対象の関数・class に対応する小文字ケバブケースにする。
- 例外として、同じ機能の関連 utility は `utils.ts`、関連する型は `types.ts` にまとめてよい。全製品の無関係な処理を集める箱にはしない。型を必要な実装のそばへ置くことも認める。
- 試験・story・schema・定数表・生成物には、対象の配置契約を使う。数を合わせるだけの helper や空の層を増やさない。
- 引数は3個まで。4個以上は `props: Props` にまとめる。
- ロジック関数は20行以内にし、純粋関数を優先する。JSX を返す部品は20行制限の対象外だが、責務が増えたら部品へ分ける。
- class は `constructor(private readonly props: Props)` と `Object.freeze(this)`。更新は `with*()` で新しい値を返し、配列は `ReadonlyArray`。保持する可変参照を外へ漏らさない。
- 業務判断と I/O を分離し、切り出した関数・class の正常・境界・失敗を直接試験できるようにする。見かけの行数ではなく、公開する振る舞いを固定する。

移動・分割前後で呼び出し元、export、外部契約、試験、build / CI を照合する。既存のテスト期待値を都合よく変更しない。製品間 package 化や配布 API の追加を内部整理に混ぜない。

依存方向と業務操作の粒度は [architecture](../design/architecture.md)、検証は [test](../../../test/SKILL.md)。
