# バグ探索と Issue の継続整理

指定された範囲でバグを探し、根拠と修正計画を Issue に残す。既存 Issue の結合・分解・依存関係・優先順位も見直し、次に調べる仕事を選び続ける。実装と PR 作成は別の依頼として [inta:dev](../dev/SKILL.md) に渡す。debug 自体は製品の修正・PR 作成・マージを始めない。

## 調査モード

| 入力 | 調査する範囲 | 実行負荷 |
| --- | --- | --- |
| 引数なし・対象だけ・`full` | コードを読み、関連テストを実行し、対象の画面を操作して確認する | 開発サーバー・テスト・ブラウザを必要に応じて使用 |
| `code` と対象 | 実装・設定・試験コード・呼び出し元・既存の結果を静的に照合する | テスト・ビルド・ブラウザ・開発サーバーを起動しない |

既定は full。`code` では、再現のためでも実行調査へ勝手に切り替えず、必要なテストや操作は Issue の検証計画として残す。既存のログや試験結果を読む場合は取得時点と対象版を確認し、今回の実行結果と表さない。

full は今回の対象に関係する実行確認を行う。画面がある製品では対象画面の正常系と問題の起きる経路を確認し、画面のない CLI・API は対応する操作や結合テストで確かめる。全スイートを無条件に回さず、[inta:test](../test/SKILL.md) で必要な検証を選ぶ。並行テストの環境・ポート・DB・CPU が競合する場合は数を絞る。

full の実行環境や権限が足りなければ、進められるコード調査を続け、テスト・画面のどこが未確認かと再開条件を残す。暗黙に code モードへ格下げしたり、フル調査済みと報告したりしない。本番の破壊的操作・実送信・課金は調査の依頼だけで行わず、検証環境やテストデータを使う。

## 開始時に決めること

対象の指示・README・実装・試験、Git の状態、既存の Issue・PR と計画を読む。対象リポジトリと探索範囲、モード、到達点（調査のみ・Issue 起票と整理）、完了条件を依頼から特定する。既にある合意は聞き直さず、結果を変える不足だけ確認する。

このスキルの実行依頼は、指定範囲の探索・Issue 起票と整理を進める依頼として扱う。「調査だけ」等の上限があればそちらを優先する。単にスキルが自動選択されたことから外部更新の許可を推定しない。Issue 整理は依頼された範囲で行い、既存の担当と人の判断を保護する。

対象が広い場合は、領域・利用経路・失敗条件から今回の探索範囲を区切る。バグや Issue の件数を成果目標にせず、何を調べ、どの根拠で判断し、何が残ったかを確認できる完了条件にする。新しい対象を際限なく追加しない。

## Goal と継続

利用者が Goal による継続を求め、クライアントが対応している場合は、現在のセッションの Goal を確認し、未設定なら作成する。目的・対象・モード・到達点・検証方法・制約・行き詰まった場合の扱いを含める。既存 Goal が今回の目的に合えば引き継ぐ。別の目的なら上書きせず、切り替えるかを利用者へ確認し、回答までは既存 Goal の変更に依存しない調査だけ進める。数値の予算は利用者が指定した場合だけ設定する。

例：「認証とセッション復元を full で並行探索し、確認できたバグと既存 Issue の重複を整理する。各 Issue に根拠・修正方針・影響・重要度・工数・完了条件を残し、次の実装候補と未決事項を示す。既存の変更を保護する。修正と PR 作成は別依頼とする。」

Goal の操作・状態遷移は、その環境で提供されたツールの説明に従う。完了は成果物と検証結果で判断し、予算終了や一部の Issue 起票を全体完了と扱わない。中断・再開・終了の指示を優先し、ユーザー管理の状態や予算を自分で変更しない。

Goal がない環境でも、同じ範囲と完了条件で今のセッションの作業を続ける。利用可否を伝え、独自の常駐プロセス・定期実行・新しいチャットを代わりに作らない。Goal は並列実行や無期限の常駐を保証するものではない。仕様の参照：[Codex Goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)。

## 並行して進める

並列作業を依頼された場合は、利用可能なサブエージェントで独立した仕事を進める。調整役は全体の目的とキューを持ち、領域ごとの探索・再現確認・Issue の計画整理を、依存関係と競合を見て配分する。使える枠と検証能力を超えて着手しない。並列機能がなければ同じキューを逐次処理し、並列実行したと報告しない。

- **探索**：領域や失敗条件を分担し、期待する契約とコード・試験コードを照合する。候補ごとに根拠、確認した版、再現条件、未確認を返す。
- **再現確認（full）**：関連テストや画面操作で候補を確かめ、実行条件と観察結果を返す。code では実行せず、コード上の経路と条件を詰める。
- **Issue の計画整理**：候補と既存 Issue・PR を照合し、同一原因の重複、独立した課題、依存関係を整理する。修正方針・影響・重要度・工数を揃え、次に実装できる課題を示す。

担当へは対象、モード、根拠、到達点、検証、既存の並行作業を渡す。担当は製品コード・GitHub を更新せず、追加の委任で無制限に担当を増やさない。同じ候補の確認は一つの担当へ寄せる。full で必要な再現用コードは、既存の変更を保護した分離環境・一時ファイルで扱い、修正コミットにしない。

調整役は、対象と根拠の版・担当・状態・Issue / 関連 PR・依存・次の一手を実行記録に保つ。複数セッションなら、対象製品が指定する共有の作業記録で担当範囲を照合する。共有の記録や排他がなければ別セッションとの同時更新を避け、探索へ回る。新しいチャットの作成・既存チャットへの送信は別途依頼された場合だけ行う。

GitHub の作成・本文更新・close は調整役に集約する。書く直前に最新の Issue・PR・担当を再取得し、別担当の更新を上書きしない。起票の応答が不明な場合は、作成済みか調べてから再試行する。

実行環境の分離は対象の規約と [worktree の初期化](../dev/references/guides/environment/worktree.md) に従う。既存の作業場所を重ねて作らず、同じ checkout でブランチを切り替えない。分離できない場合は読み取りの探索を並行し、実行確認は逐次にする。code モードでは実行環境の構築を始めない。

## 探索と整理の循環

1. **現在地を確認する。** 既存の担当・進行中 PR・関連 Issue と今回の範囲を照合する。再開時は実行記録だけを信用せず、最新のコードと GitHub の状態を確認する。
2. **根拠を集める。** full では再現できる試験や最小操作で確認し、code では契約・呼び出し経路・条件を静的に追う。推測・環境要因・好みだけを確定バグにしない。コード上の確定した欠陥と実環境での発生確認を区別し、未確認境界を示す。
3. **Issue の計画を整える。** [Issue・PR の正本](../dev/references/tools/issue-pr.md) に従い、既存への追記・新規・結合・分解を選ぶ。修正の方向性と、影響・重要度・工数の根拠が揃ったか確認する。未決なら、必要な調査・判断を次の仕事にする。実装修正で試さないと決められない場合は、その検証計画を残す。
4. **次の実装へ渡せるか確認する。** 完了条件、依存先、推奨する検証が揃った Issue を示す。PR は既存の状態と関連付けを読み、解決済みか・一部だけかを照合する。debug から dev や PR 作成を自動起動しない。
5. **キューを見直す。** 発見した原因が別の Issue にも影響するか、分解・依存・優先順位が変わるかを照合する。未調査・確認中・Issue 整理中・実装候補・他担当が修正中・判断待ちを区別し、次の独立した仕事を進める。

Issue の本文・属性・整理の基準は上の正本に集約する。`check` の読み取り専用という契約を変更したり、通常の `dev` から全体探索を自動実行したりしない。

## 完了と引き継ぎ

今回の範囲を指定モードで調べ、候補の採否に根拠があり、Issue の計画・属性・関連付けが整理されたことを確認する。修正と PR 作成は debug の完了条件に含めない。full の実行確認が残る場合は完了を偽らず、残る条件を示す。

進捗のない探索・同じ失敗の再試行・同じ文面のコメントを繰り返さない。必要な権限・再現材料・方針判断が足りず進める仕事もなくなったら、試した経路と根拠、残作業、再開条件を示し、Goal の状態はその環境の停止条件に従う。

最後はモードと調べた範囲、コードで確認した欠陥と実行で確認した事象、Issue の新規・更新・結合・分解、未確認・判断待ち・次の実装候補を短く報告する。修正を進める例は `/inta:dev #123 を修正してPRまで`。別セッションへの送信や自動着手は含めない。
