# code — lint / test 起点のコード・テスト・構成の是正

`/product:maintain code [scope]`は、確認済みの[product:check code](../../check/commands/code.md)結果を起点に、コード・テスト・ディレクトリ構成の一系統だけを規約へ寄せる。感触ではなく現在のtool出力とcall pathから始める。

# 手順

1. 人間が指定したscopeと`product:check code`のfindingを確認する。結果が無ければ同じscopeを読み取り専用で点検する。対象リポジトリが定めるformat / lint / typecheck / test / buildを確認し、今回の範囲に必要な標準commandを実行する
   - 未使用検出があれば実行（knip 等）
   - リポジトリ固有のカスタム lint（`scripts/check-*` 方式のもの）
   - 手書きの実装ファイルを行数順に並べる。テスト、fixture、生成物、migration、schema／マスタデータは実装と分けて集計し、同じ順位表で比較しない
   - 800 行超を点検候補、1,500 行超を優先候補として記録する。行数だけを理由に自動分割はしない
   - 大量移動や構成変更が候補なら、変更前の対象ファイル一覧、export一覧、import／利用箇所、root workspace設定、lockfile、CI / deployの対象pathと実行commandを機械的に採取する
2. 出力を分類する
   - 赤（失敗・エラー）: 最優先。ただし挙動変更が要る修正は別の`product:dev`候補へ分離
   - 黄（警告・skip・deprecated）: 今回選んだ一系統だけ直し、判断が要るものは確認リストへ
   - 未使用（dead code・未使用 export・未使用依存）: language serviceとcall pathで参照ゼロを再確認してから削除する。生成物・CLI管理下・再生成で復活するものは削除しない
3. テストの質を点検する
   - 消えた機能を検証し続けているテスト（実装側に対象が無い）は削除
   - flaky の兆候（リトライ・sleep 頼み・日時依存）は今回scopeで安定化するか、別作業候補へ分離
   - 実装変更に追従していない skip は、直すか削除かをオーナーに確認
4. ディレクトリ構成と巨大ファイルを dev スキルの Code Design へ寄せる
   - 置き場所違反のファイルは移動し、import を追従させる
   - 肥大化したディレクトリはドメイン単位の分割を提案する（大規模な移動は単独 PR に分離。機能変更と混ぜない）
   - 巨大ファイルは、DB 読み込み、検証、変換、永続化などの責務と、依存するデータ／サービスのまとまりを先に列挙してから境界を決める
   - 行数だけを移す helper、単一関数を包む static-only class、クラス名だけのディレクトリ、共有されない `types.ts` を作らない
   - 関連する依存と複数操作を一つの入口から使うならクラス、単一の入力→出力なら関数にする。分割先の都合で呼び出し側の組み立てが複雑になる場合は Facade を置く
   - 振る舞いを持つ切り出し先には直接テストを置く。既存の結合テストだけで担保する場合は、そのテストがどの責務を保護するかを報告する
5. 配置境界を次の順で判定し、構成拡張を内部整理から分離する

   | 条件                                       | 既定の判断                                                      |
   | ------------------------------------------ | --------------------------------------------------------------- |
   | 同一製品・同一release・内部利用            | `src/lib`など、その製品の既存package内へ置く                    |
   | 再利用可能、ライブラリ化                   | 既存package内の内部libにする。workspace / package化はしない     |
   | 複数の具体的な利用製品と独立依存境界がある | private workspaceを選択肢として提案する。明示承認までは作らない |
   | npm公開・外部配布                          | ユーザーが公開または配布を明示した場合だけ配布設計へ進む        |
   | 判断材料が足りない                         | 内部配置を維持し、構成を変える前に確認する                      |

   次の入力例を回帰判定として固定する。

   | 入力                                | 判定                                                         |
   | ----------------------------------- | ------------------------------------------------------------ |
   | 「ライブラリにして」                | 内部lib。package化しない                                     |
   | 「別製品でも使えるように」          | 具体的な利用製品と依存境界を確認する。まだpackage化しない    |
   | 「private workspace packageにして」 | 構成拡張の明示あり。影響確認後にworkspace化してよい          |
   | 「npmで公開して」                   | 配布の明示あり。公開範囲とversioningを確認して配布設計へ進む |

6. 仕上げに 1 の全コマンドと行数順位を再実行し、次を満たしたことを確認する
   - 標準検証が開始時より悪化していない（テスト数の減少は削除理由を報告に明記）
   - 元ファイルから切り出した責務と重複実装が消え、元ファイルは調整役へ近づいた
   - 分割先は単独で意味のある API を持ち、元ファイルより大きい新たな巨大ファイルを作っていない
   - 対象が最大級の実装ファイルに残る場合は、残した責務と次の分割候補を報告する
   - 移動前後の対象ファイル、export、import／利用箇所を全数照合し、欠落、重複、意図しない公開範囲の変更がない
   - `package.json`、lockfile、workspace設定の差分から、workspace追加、`exports`、独立version、`dist`、publish scriptの新設を検出する。依頼に含まれない構成拡張は差分から除く
   - 明示されたpackage / workspace変更がある場合は、root workspaceとlockfileの整合、影響する全製品のCI / deploy対象と標準検証を確認し、結果を報告する

# 実行の分割

独立した機械変更は利用可能な並行手段へ分けてよい。設計判断、同じfile、共有APIに触る変更は一つの責任者が統合する。特定のagent名を前提にしない。

# 禁止

- 挙動の変更（バグ修正を含む）をリファクタに混ぜること。見つけたバグは Issue に起票して分離する
- 緑にするためにテストの期待値を実装に合わせて書き換えること（それは挙動変更の隠蔽）
- 生成物・CLI 管理ファイルの手編集
- 行数を減らすこと自体を目的に、意味の無い class／directory／helper を増やすこと
- 「再利用可能」「ライブラリ化」だけを根拠に、workspace / package、独立した配布物・version、公開APIを追加すること
