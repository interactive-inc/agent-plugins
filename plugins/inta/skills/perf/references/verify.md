# 同値を証明し、退行を止める

性能改善は「速くなった」だけでは受け入れられない。結果が変わっていないこと、次の変更で元に戻らないこと、配信後に本当に効いたことの 3 つを示す。

## 目次

- 結果が変わっていないことを示す
- 退行を止めるテスト
- 配信後の確認
- 数字の扱い
- 記録の型

## 結果が変わっていないことを示す

- 変えるクエリは、本番で新旧を読み取り専用で実行して比べる。同じ引数で旧 SQL と新 SQL を実行し、結果のハッシュの一致と、読み行数・実行時間の差を記録する。返す行数が同じでも、並び順や NULL の扱いが変わっていないかをハッシュで見る
- 変える前に、今の結果を固定するテストを足す。境界ケース（在籍・休職・退職、開始前、期間が 2 つ重なる、紐付けの無いデータ、別テナント、将来日付の訂正）を列挙し、変更前に緑であることを確かめてから実装を変える
- 共有・絞り込みの経路は、ある場合と無い場合の両方で同じ結果になることを示す。取得窓で絞った読みと全件の読みで集計結果が一致する、共有入力を渡した場合と渡さない場合で全行が一致する、など
- 権限の境界を必ず含める。速くするための書き換えで、他人・他テナント・範囲外のデータが混ざっていないか。割当なし、停止・削除済み、将来の失効も確かめる

## 退行を止めるテスト

本番でしか見えない量（往復の待ち、本番規模の読み行数、上限）を、ローカルのテストで代わりに測れるようにする。

### 段数とクエリ本数の上限

ローカルの DB には往復の待ちが無いので、ms ではなく「直列の段数」と「クエリ本数」に上限を置く（上限は対象製品の変更前の値と要求から決める）。

段数の数え方: DB クライアントの prepare（文の実行）をフックして本数を数え、同じ同期ブロックの中で走った文を 1 段とする。最初の文で段を 1 つ進め、microtask の境界でフラグを戻す。並列に発行した読みは同じ同期ブロックに並ぶので 1 段になり、await で microtask へ戻ったときだけ次の段になる。

```ts
export function countStatements(db: { prepare: (sql: string) => unknown }) {
  const prepare = db.prepare.bind(db)
  let statements = 0
  let stages = 0
  let isSameStage = false
  db.prepare = (sql: string) => {
    statements += 1
    if (!isSameStage) {
      stages += 1
      isSameStage = true
      queueMicrotask(() => {
        isSameStage = false
      })
    }
    return prepare(sql)
  }
  return () => ({ statements, stages })
}
```

ドライバの実装によって、prepare が同期で走るか、クエリビルダが遅延評価されるかが違う。数える対象のドライバで、並列の読みが 1 段に数えられることを最初に確かめる。

カウンタの値の読み方:

- 数えているのは microtask の区切りであり、DB の往復の依存ではない。並列に渡したクエリビルダ（thenable）の解決や、Promise でない値の await で区切りがずれ、同時に飛んでいる読みが別の段に数えられることがある。カウンタの段数は、実際の依存の深さ以上の値になる
- そのため報告では、カウンタの値（退行を止める上限に使う）と、コードを読んで数えた依存の深さ（本番の往復の目安）を分けて書く。カウンタを依存の深さまで縮めることを目標にしない
- 文をキャッシュして prepare を呼ばないラッパー（テスト用の D1 ラッパーなど）を通る読みは数えられない。数えたい読みが別の接続やラッパーを通っていないかを確かめる

### 他人のデータが増えても読み行数が増えない

本人分だけ読むべきクエリは、他のアカウント・テナントのデータを大量に置いた状態で、読み行数が一定以下であることを確かめる。読み行数は DB が返すメタ情報（D1 の `rows_read` など）か、EXPLAIN で取る。

### 実行計画を固定する

索引を足した・変えたとき、またはクエリの形を変えて計画を変えたときは、EXPLAIN の結果で「この読みは新しい索引を使う」「この CTE は使わない」「`SCAN <表>` が無い」を固定する。部分索引の述語がずれると黙って全走査に戻るため。計画は統計（`sqlite_stat1`）の有無で変わるので、テストの中で前提の統計の状態（行が無い、またはある）も確かめる。

### 本番の上限をテスト DB で再現する

テスト用の DB は、本番の上限（1 文の bind 数、行サイズ、batch の大きさ）よりずっと緩いことが多い。テスト用のラッパーに本番と同じ上限を任意で有効にする口を作り、件数に比例して bind が増える経路のテストで有効にする（例: `maxBoundParameters`）。修正前のコードで落ちることも確かめる。

### メモリと起動の予算

ビルド成果物を本番と同じランタイムで起動し、代表の route を呼んだ後の heap を測り、予算（例: 128MB 上限に対して 96MiB）を超えたら落とす。入口から静的に辿れるファイルの合計サイズも、変更前後を同じ手順で比べる。

### 本番規模の fixture

施設数・利用者数などを本番に合わせたローカル DB を作り、ベンチを任意実行のテストとして置く（製品の試験で明示的に有効化する）。通常のテストでは回さない。

## 配信後の確認

- 配信した版が本番で動いていることを確かめる（Worker の version、配信アセットのハッシュ、デプロイのジョブ結果）。ヘルスチェックは疎通の確認であり、性能の確認ではない
- 変更前と同じ API・同じアカウント・同じ回数で測り直す
- DB の統計で、新しい SQL が実際に使われ、読み行数が想定どおりであることを確かめる
- 配置を変えたら、配置先を示す応答ヘッダを確かめる
- 改善しなかった・悪化した場合の戻し方（索引の DROP、設定の削除、revert）を先に決めておく

## 数字の扱い

- 少数標本（各 3 回など）はそのまま書く。中央値・最遅値・標本数を併記し、p95 や「全利用者で」とは書かない
- 初回（cold）と再読込（warm）を混ぜない
- CPU 時間と経過時間（wall）を分けて書く。Workers のように時計が I/O の完了でしか進まない実行環境では、Server-Timing の値は I/O 待ちであり CPU ではない。並行して走る工程の値は重なるので合算しない
- SQL 単体の実行時間や読み行数、ローカルの段数の改善を、画面の速さの改善として書かない。配信後に画面か API で測り直す
- 配信前と配信後は同時に比べた A/B ではない。小さな差を変更の効果と断定しない
- 外部の障害やデータ量の増加が原因に見えても、計測で裏づけるまでは断定しない

## 記録の型

PR の説明や Issue に、直した 1 件を残すときの型。

```markdown
## 変更前

- 対象: `GET /api/...`（<アカウント種別>、本番、<日時> JST、各 <N> 回）
- 中央値 <ms> / 最遅 <ms>。Worker CPU 最大 <ms>
- 原因: 権限取得の SQL が派生表の外側でしか本人を絞らず、1回に<読み行数>行を読む（`<path>:<line>`、EXPLAIN で SCAN）

## 変更

- 派生表の内側で本人に絞る（視点: 派生表）。返す行・権限の判定は変えない

## 証明

- 本番で新旧 SQL を読み取り専用で実行し、同じ結果・ハッシュ一致。読み行数 <変更前> → <変更後>
- 他アカウントの合成データを増やしても読み行数が増えない試験

## 変更後

- 配信後、同じ条件で各 <N> 回。中央値 <ms> / 最遅 <ms>
- 本番の DB 統計で新SQLが平均<読み行数>行

## 残り

- <解消していない項と、未確定の原因>（Issue #<番号>）
```
