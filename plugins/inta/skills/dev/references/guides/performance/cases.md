# 性能改善を考える架空例

以下は説明のために作った架空の構成と数字で、実在の製品・顧客・計測結果・作業履歴ではない。実際の改善では対象製品で測り直し、同値性と権限を確かめる。

## 直列の待ち

独立した4回の読み取りを一つずつ待っている架空のAPIを考える。前の結果を使わない読み取りだけを同時に始められれば、結果を変えずに待ちの段数を減らせる。実際の所要時間は環境と負荷によって変わる。

## 読み行数

架空の複数利用者向けの表で、全利用者を読んでから本人分に絞る処理を、DBの読み取り時点で本人に絞る処理へ変える。結果・順序・権限が同じで、他の利用者のデータが増えても読み行数が増えないことを試験する。

## 別の処理への影響

架空の検索処理へ索引を追加するときは、その検索だけでなく同じ表を読む別の処理の計画も比べる。試験環境だけで速くても、本番相当の分布と統計で悪化しないことを確認できなければ、適用の判断を利用者へ返す。

実際の製品の記録は、その製品で許可された保存先へ残す。機密の計測値・地域・認証構成を共通スキルへ持ち込まない。
