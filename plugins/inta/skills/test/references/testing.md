# 仕様トレーサビリティとテスト戦略

仕様、Application、テストを安定した仕様IDで結び、symbol名やファイルパスを仕様の正本にしない。IDの存在は追跡可能性、テストの実行結果は振る舞いの証拠として分ける。

## 仕様IDで紐付ける

利用者の目的と受入条件を `.docs` のFeatureまたはStoryへ書き、リポジトリ内で一意なIDを持たせる。コード側では、その操作を所有するApplicationユースケースクラスが同じIDを宣言する。一つのクラスが複数Featureを所有してはならない。

```yaml
id: 00480001
tags: [application-use-case]
```

```ts
/** ログイン用メールアドレスを追加する。 */
export class AddLoginEmail {
  static readonly featureId = "00480001"

  async execute(input: AddLoginEmailInput): Promise<AddLoginEmailResult> {
    // 業務操作
  }
}
```

文書へsymbol名やファイルパスを書かない。監査がIDから現在のowner symbol、パス、テスト証拠を生成する。関数・クラス・メソッドのリネームや移動ではIDを変えず、業務上別の操作へ分割・統合したときだけ仕様との対応を見直す。

一つのApplicationユースケースクラスは一つの子Featureへ対応させる。複数のユースケース、画面、外部連携を横断する利用者の完了条件はStoryへ書き、一つの巨大なownerやFacadeへまとめない。

テストにも同じIDを宣言する。記法はリポジトリで統一し、たとえば操作の証拠を `[feature:00480001]`、利用者の完了条件まで通した証拠を `[acceptance:00480001]` とする。

CIでは次を失敗にする。

- 移行済み仕様に対応するApplication ownerがない
- Applicationの仕様IDに対応文書がない
- 一つの操作IDを複数ownerが所有する
- テスト済み・受け入れ済みの文書に対応するテスト証拠がない
- 文書、owner、テストでIDが食い違う

既存製品を一括で必須化しない。未紐付けApplicationは監査キューとして全件表示し、Feature単位で仕様とテストを確認してから厳格管理へ移す。新規または移行済みFeatureには例外を作らない。

## テストの正を分ける

### Application / Domain — 業務判断の正

業務ルール、状態遷移、不変条件、対象範囲、境界値、再実行、途中失敗、並行実行を検証する。実ローカルDBなど決定的な依存を使い、外部サービス境界だけを制御可能なadapterへ置き換える。

認可判断は、その製品で認可を所有する層で検証する。認可をInterfaceかApplicationのどちらかへ一律固定しない。

テストコードもproductionと同じ層境界ルールに従う。実DBの組み立てやschema参照がその層の禁止importに当たる場合は、境界ルールの対象外に置いたテスト専用ハーネスへ切り出して参照を1本化し、テストのためにルールを緩めない。

### エンドポイントE2E — HTTP契約の正

ルートをHTTP境界から実行し、メソッドとパス、入力変換、認証・認可の接続、status、body、header、Cookie、エラー変換を検証する。実ネットワーク接続は必須ではなく、ルートへHTTPリクエストとして入って実DBまで通ればよい。

正常系は代表1本、拒否・入力不正・競合など契約ごとに代表例を置く。Applicationで検証済みの計算表、境界値、状態遷移をHTTP越しに繰り返さない。認可判断をApplicationが所有する場合、判断の組合せはApplicationで、403への変換はエンドポイントで検証する。

形式バリデーション（必須・型・範囲などスキーマ宣言で表せるもの）は網羅テストを書かない。網羅はスキーマ宣言自体が担い、エンドポイントでは不正入力の代表1本でスキーマの配線だけを固定する。相関チェック・状態依存の業務バリデーションはApplication / Domainで境界値を尽くす。

### ユーザージャーニーE2E — 利用者の完了条件の正

複数画面・エンドポイント・外部連携を通り、利用者が目的を達成できることを検証する。全エンドポイントに作らず、Storyの完了条件ごとに作る。

たとえば「管理者がメールを追加し、本人がメールを受け取り、パスワードを設定してログインする」は、追加APIの200やDB行だけでは完了しない。画面、API、DB、メール受付、リンク、パスワード設定、実ログインまで通す。メールサービスの受付、配送、受信箱への到達は別の事実として扱う。

### コンポーネント — UI 表示状態の正

データ取得を含むコンポーネントは、API を MSW でモックして fetch → client → queryFn の実経路を通し、表示状態（データあり・空・失敗）を検証する。props レベルのモックでは実経路の配線ミス（URL 誤り・パース失敗・エラーの握り潰し）を検出できない。

ハンドラ定義は Storybook の story と共有し、テストが検証した状態と story で見える状態を同じ契約に乗せる。未定義リクエストはエラーにして、ハンドラ漏れを「空データで緑」に化けさせない。

### スモーク — 配線の正

ルーターや契約定義から全操作を自動列挙し、設定した認証情報で到達でき、予期しない5xxにならないことを検証する。個別の業務仕様やレスポンス詳細を重複検証しない。

## 潜在仕様バグを探す

正常系だけで受け入れ済みにしない。各Featureの開始状態、成功後、失敗後を明記し、少なくとも次を検討する。

- 永続化の途中だけが失敗したとき、再試行できるか
- 同じ操作を2回または同時に実行して不変条件を壊さないか
- 対象が0件、1件、複数件のとき、別対象へ影響しないか
- 旧データ、null、期限境界でも対象を取り違えないか
- 外部送信失敗時に、それまで使えた経路やデータを失わないか
- API成功や外部サービス受付を、利用者の完了と誤認していないか

再実行の正解は操作の意味論で決まる。イベントの追記（記録の登録など）は2回実行で2件残るのが正しく、希望状態を送る宣言的な差分適用は何回実行しても結果が変わらない（冪等）のが正しい。テストはどちらの意味論かを明示して固定する。

検討したうえでテスト化しない観点は、理由を添えてテストファイルへ残す。後から読む人が「検討済みで不要」と「検討漏れ」を区別できるようにする。

仕様ID監査は「何が未接続か」を見つける。これらの状態・失敗・時間軸のテストは「接続された実装の意味が正しいか」を見つける。両方を完了条件にする。
