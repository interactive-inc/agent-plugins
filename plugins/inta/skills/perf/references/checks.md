# 視点ごとの見つけ方と直し方

各視点について、候補の見つけ方、本物と確定する条件、直し方、直したことの確かめ方、直さないときを書く。候補の多くは `scripts/find-candidates.sh` が拾う。拾えない視点（前段・重複・不要計算・再構築など）は、ここに書いた読み方と計測で見つける。

実在の製品の計測記録は含めない。説明用の構成は [cases.md](cases.md) の架空例を参照する。SQL は SQLite（D1）で書いているが、考え方は他の DB でも同じである。

## 目次

- サーバと DB の視点: 前段、段数、行ごと、重複、不要計算、派生表、述語、相関、全件、索引、bind、取得量、再構築
- 画面と起動の視点: 連鎖、境界、起動待ち、入口、配信資産、無効化
- 直さずに判断を仰ぐ視点: 距離、キャッシュ、認可情報のトークン化

## サーバと DB の視点

### 前段

全 API が通る共通の前段（認証・セッション・権限・テナント解決）の往復と読み行数。1 往復・数千行の差が全画面に効くので、範囲の指定が無ければ最初に見る。

- 見つけ方: 認証・認可の middleware と、そこから呼ぶ読み取りを辿る。段数カウンタ（[verify.md](verify.md)）を軽い API 1 本に当て、前段だけの段数と本数を数える。本番の DB 統計があれば、回数が最も多いクエリが前段のものかを見る
- 確定の条件: 前段が 2 段を超える、本人分だけを読むべきクエリが他人の行まで読む（下の「派生表」「述語」）、同じ情報を前段とハンドラで 2 回読む
- 直し方: 同じ batch へまとめる、内側で本人に絞る、ハンドラは前段が解決した値を受け取って読み直さない
- 確かめ方: 他人のデータを大量に置いても本人の読み行数が増えないテスト（[verify.md](verify.md)）、権限の境界（割当なし・停止・削除・将来の失効）の既存テストが緑
- 直さないとき: 認証結果や権限を TTL キャッシュで省く変更はしない（下の「認可情報のトークン化」）

### 段数

互いに依存しない読みが、await で直列に並んでいる。

- 見つけ方: スキャナの「段数」2 項目（連続した await、await の多いファイル）。オブジェクトのプロパティや関数の引数の中の await（`employees: await ...`、`new X(await ...)`）も直列の段になる。API の経路なら、段数カウンタでハンドラ全体を実測し、コードを読んで依存の深さ（前の結果を本当に使う読みの連なり）も数える
- 確定の条件: 後の読みが前の結果を使っていない、または結果のごく一部（ID・月など）しか使っていない
- 直し方: DB に batch（複数文を 1 往復で送る機能）があれば batch で 1 段にする。無ければ並列に発行する。結果の一部しか使わない依存は、その値だけを軽く先に解決するか、同じ batch の先頭に入れる。逐次の分割読み（100 件ずつ順に等）は、基準（版・時点）を先に固定してから上限付きで並行にする
- 確かめ方: 段数とクエリ本数の上限テストを足し、変更前より小さい値で固定する。結果の一致を既存テストか新しい一致テストで示す
- 並列にしてよい範囲: どのみち発行する読みだけを同時に出す。存在確認のように、失敗すれば後続が要らなくなる読みは先の段に残す（存在しない施設に十数本の読みを撃たない）。結果次第で不要になる読みを先回りで発行しない。同時に発行する文の数が大きく増えるときは、報告に書く
- 直さないとき: 書き込みの順序に意味がある処理（トランザクションの途中、楽観ロックの確認）

落とし穴: 2 本の SQL を 1 本にまとめたとき、絞り込み条件が派生表の外へ出ることがある。往復は減っても読み行数が 100 倍になった例がある。まとめた後は必ず読み行数を前後で比べる。

### 行ごと

ループや `.map(async ...)` の中で、1 行ごとに DB を呼ぶ（いわゆる N+1）。

- 見つけ方: スキャナの「行ごと」。ORM の relational query がループ内にある箇所も含める
- 確定の条件: ループの回数がデータ件数（利用者数・施設数など）に比例し、その中で DB を呼ぶ
- 直し方: ID を集めて 1 回の IN（上限があればチャンク）で読み、Map で引く。書き込みなら batch にまとめる
- 確かめ方: 件数を 1 件と N 件で変えて、クエリ本数が一定であることをテストする（例: 1 人と 3 人で読み取り本数が同じ）
- 直さないとき: 回数が小さな定数で上限がある（月 3 種など）、外部 API のレート制限で直列が必要

### 重複

1 リクエストの中で、同じ表・同じ行集合を部品ごとに読み直す、同じ重い計算を 2 回する。

- 見つけ方: 段数カウンタで実行された SQL を記録し、同じ文が 2 回以上出るかを見る。本番の DB 統計で「1 リクエストあたりの回数」が 1 を超えるクエリを探す
- 確定の条件: 同じ引数で同じ行集合を読んでいる、または同じ入力から同じ結果を計算している
- 直し方: 呼び出し側で 1 回読み、引数で渡す。共有はそのリクエストの中だけにし、リクエストをまたぐキャッシュにしない（書き込みの後に古い値を返すため）
- 確かめ方: 共有入力を渡した場合と渡さない場合で、全出力が一致するテスト。読み取り本数が減ったことを段数カウンタで示す

### 不要計算

重い処理を呼び、その結果の一部しか使っていない。

- 見つけ方: 集計・分析系の関数の戻り値のうち、呼び出し側が実際に読むフィールドを数える。重い処理（多段の読み・全期間の計算）なのに 1〜2 項目しか使っていない箇所。権限で伏せる値を、読んでから最後に null や既定値で上書きしている箇所も同じ形である（閲覧者が見られない売上・料金を毎回集計している等）
- 確定の条件: 使う値を、より少ない読みで同じに出せる
- 直し方: 使う値だけを出す軽い読み取りに差し替え、重い処理は本来の画面に残す（例: 全期間の集計ではなく表示する期間だけ読む）。伏せる値は、伏せる条件のときに読み取り自体を出さない。伏せる処理は外側に残し、応答の形とキーの順を変えない
- 確かめ方: 差し替え前後で、使っている値が一致するテスト。伏せる場合は、伏せられる閲覧者の応答が変更前と完全に一致することと、その閲覧者の SQL に対象の表が現れないことをテストで固定する

### 派生表

JOIN の右側のサブクエリや CTE が、外側の WHERE の条件を受けずに全件を組み立てる。

- 見つけ方: スキャナの「派生表」と「相関」。EXPLAIN で `MATERIALIZE` や、外側で絞っているのに内側が `SCAN` になる箇所
- 確定の条件: 外側の WHERE で絞る列（本人の ID など）が派生表の内側の WHERE に無く、読み行数が返す行数より桁違いに多い
- 直し方: 同じ条件を派生表の内側にも書き、索引を使わせる

```sql
LEFT JOIN (
  SELECT binding.account_id, permission.permission_key
  FROM role_bindings AS binding
  INNER JOIN roles AS role ON role.id = binding.role_id
  LEFT JOIN role_permissions AS permission ON permission.role_id = role.id
  WHERE binding.account_id = ?1
) AS grant_row ON grant_row.account_id = account.id
WHERE account.id = ?1
```

- 確かめ方: 新旧 SQL の結果ハッシュの一致と読み行数の差（結果と順序を維持したまま読み行数が減ること）。他人のデータを大量に置いても読み行数が増えないテスト

オプティマイザが外側の条件を内側へ押し込めるとは限らない。特に LEFT JOIN の右側、集計・窓関数・DISTINCT・UNION を含む派生表では、内側を全件組み立てることがある。

### 述語

索引がある列なのに、条件の書き方のせいで索引が使われない。

- 見つけ方: スキャナの「述語」2 項目（LIKE の前方一致、列に式をかけた条件）。異なる列の OR、暗黙の型変換も見る
- 確定の条件: その列に索引があり、EXPLAIN が `SCAN` を返す
- 直し方:
  - 列に式をかけた条件（`substr(month, 1, 4) = '2026'` 等）は範囲条件（`month >= '2026-01' AND month < '2027-01'`）にする
  - SQLite の `LIKE` は既定で大文字小文字を区別しないので、BINARY 照合の索引で前方一致の範囲検索にならない。数字のコードなど区別の要らない固定の前方一致は `GLOB '42*'` にする。ワイルドカードの記法（`*` `?` `[...]`）が `LIKE` と違うので、値に記号が含まれうるときは置き換えない
- 確かめ方: EXPLAIN が `SEARCH ... USING INDEX` に変わること。新旧の結果集合の一致（本番で読み取り専用で比べるのが確実。できなければ境界の値を含む fixture で）
- 直さないとき: 索引が無い列（「索引」の視点で判断する）、大文字小文字を区別しない検索が仕様である

### 相関

SELECT の中の相関サブクエリが、外側の行ごとに CTE・窓関数・集計をやり直す。表が小さくても掛け算で数十万行になる。

- 見つけ方: スキャナの「相関」（`sql.raw` の展開、SELECT 内のサブクエリ）。EXPLAIN の `CORRELATED SCALAR SUBQUERY`
- 確定の条件: 相関サブクエリの中に CTE・窓関数・集計があり、読み行数が「外側の行数 × 内側の表の行数」に近い
- 直し方: 「1 件につき 1 行」の派生表（例: 雇用ごとの現在の状態）を相関させずに 1 文で 1 回だけ計算し、ID で結合する
- 確かめ方: 変更前の応答を固定するテストを先に足し、境界ケース（期間の重なり、紐付けの無いデータ、開始前・終了後）を含めて前後で緑。1 件だけ読む詳細系は、かえって増えることがあるので経路ごとに測る

### 全件

WHERE の無い読み取りを、アプリ側で絞る・数える。

- 見つけ方: スキャナの「全件」。読んだ後に `.filter(` や `.length` だけを使う箇所
- 確定の条件: 表が件数とともに増える（利用者・明細・履歴など）。小さな固定のマスタは対象外
- 直し方: 絞り込みを SQL へ移す。件数だけなら COUNT。画面に出す期間（選択月・累計・前月・前年同月）だけ読む
- 確かめ方: 絞った読みと全件の読みで、出力が一致するテスト

### 索引

計測で全走査が確定し、述語の書き換えでは足りないときに索引を足す。

- 見つけ方: 本番の DB 統計で読み行数の合計が上位のクエリ、EXPLAIN の `SCAN`、`USE TEMP B-TREE`。WHERE で範囲を絞っていても、その列を先頭に持つ索引が無ければ全走査になる（日付の範囲で絞るのに、索引が `(利用者, 日付)` しか無い等）。これは字句では見つからないので、範囲内の読み取りの EXPLAIN で見つける
- 確定の条件: WHERE / JOIN / ORDER BY の列に合う索引が無い。DISTINCT や集計なら、対象列を含む covering index で表を読まずに済む
- 直し方: 対象リポジトリの migration の手順で足す。一部の行だけを速く読みたいなら、述語付きの部分索引にする
- 確かめ方: 同じ表を読む他のクエリを列挙し、本番と同じデータ量で EXPLAIN を前後比較する。追加後は同じ表を読む全クエリの読み行数を監視する
- 直さないとき: 本番相当のデータで他のクエリの計画を比べられないなら、索引は足さずに根拠付きで提案に留める。索引の追加で別のクエリの計画が悪化する可能性がある。予防的に足さない

部分索引の影響範囲は、述語から絞れる。部分索引を使えるのは WHERE が索引の述語を含むクエリだけなので、述語（例: `product_code IS NOT NULL`）をコードから検索してその全クエリを列挙し、それぞれの EXPLAIN を前後で比べる。提案に留めるときも、この列挙と比較を根拠に付ける。

統計の有無で計画が逆転することがある。SQLite は `sqlite_stat1`（`ANALYZE` や `PRAGMA optimize` が作る）があると索引の選び方を変える。統計の有無の両方で、変更前後を確認する。

- 本番に統計があるかを、読み取り専用の `SELECT tbl, idx, stat FROM sqlite_stat1 WHERE tbl = '<表>'` で確かめる。ローカルの EXPLAIN は本番と同じ統計の状態で取る（統計の行を消すか入れるか）
- 確かめられないときは、両方の状態で EXPLAIN と読み行数を取り、どちらでも悪化しない変更だけを直す
- 恒真の条件（`id IN (SELECT id FROM 親表)` など、結果を変えない条件）を足してプランナに別の索引を選ばせる書き換えは、統計が入ると逆効果になりうる。直さずに、構造的な直し（部分索引・索引の列順）を推奨案として提案する

### bind

件数に比例して bind 数が増える文が、上限（D1 は 1 文 100 個）を超えて失敗する。性能というより件数が増えたときの故障だが、同じ読み取り経路にあるのでここで扱う。

- 見つけ方: スキャナの「bind」（変数の配列を渡す IN、変数を渡す複数行 INSERT、生 SQL の `IN (${...})`）
- 確定の条件: 配列の長さに上限が無い（利用者数・明細数に比例する）。チャンク用の共通関数を通っていない
- 直し方: IN は上限以内にチャンクする。行ごとの条件を OR や CASE で並べる代わりに、JSON 1 個を `json_each` で照合する。複数行 INSERT は 1 文の行数を「上限 ÷ 列数」で計算する
- 確かめ方: テスト用 DB に本番の上限を再現する口を作り、上限を超える件数で修正前は落ち、修正後は通ることを示す

### 取得量

画面に出さない項目・ページ外の行・期間外の月まで返す。

- 見つけ方: 応答サイズの大きい API（数百 KB）、選択肢やサイドバーが全項目の一覧 API を使っている箇所、一覧の付属情報を全件分読む箇所
- 確定の条件: 呼び出し側（画面・コンポーネント）が実際に読むフィールドが、返している量よりはっきり少ない
- 直し方: 既存の形を残したまま、用途別の軽い形（例: `view=directory`）を追加し、使う側を切り替える。軽い形を使う画面同士はキャッシュキーを共有する。付属情報は表示中のページ分だけ読み、検索のための全件検索は残す
- 確かめ方: 軽い形の値が全項目の形の該当部分と一致するテスト。権限の範囲・並び順が同じであること
- 直さないとき: 既存の応答から項目を削る変更（外部や CLI の利用者を壊す）。実数が要る画面を機械的に軽い形へ置き換えない

### 再構築

ループの中で、同じ索引・Map・表を作り直す。CPU が数百 ms 以上の API に多い。

- 見つけ方: スキャナでは拾いにくい。CPU の大きい API を、工程別の時間かプロファイルで分け、大きいところのループを読む
- 確定の条件: ループの外で 1 回作れば足りるものを、反復ごとに作っている
- 直し方: 1 回だけ作って渡す。月ごとに同じ履歴を読み直しているなら、期間分をまとめて 1 回読む
- 確かめ方: 出力の一致。計測で大きくなかった箇所は触らない

## 画面と起動の視点

### 連鎖

前の取得の結果を待ってから、次の取得を始める。

- 見つけ方: スキャナの「連鎖」（`enabled` が前の `data` に依存）。ブラウザの network で、ある要求の完了直後に次の要求が始まっている箇所
- 確定の条件: 後段が使う値（当月・確定月など）を、前段の重い取得を待たずに決められる
- 直し方: 後段が要る値を軽い取得で独立に決めるか、サーバの同じ読み取りで合成する
- 確かめ方: 実ブラウザで、要求が並行に始まることを network で確かめる。表示される値が変わらないこと
- 直さないとき: 後段の要求がログイン状態や権限で決まる（未ログインで出すと無駄になる）

### 境界

独立したデータを、同じ待ちの境界（Suspense・ローディング単位）で待つ。1 つの遅い取得が区画全体を止める。

- 見つけ方: スキャナの「境界」（1 ファイルで 2 つ以上の取得を待つ）
- 確定の条件: 区画の中に、遅い取得を待たずに描ける部分（人数・名簿など）がある
- 直し方: 先に描ける部分を別の境界に分ける（例: 一覧を補助的な絞り込み候補より先に表示）
- 確かめ方: 遅い方の応答を遅らせた状態（テストで応答を保留する等）で、先の部分が表示されることを実ブラウザで確かめる。レイアウトが崩れない（読み込み表示の高さ）

### 起動待ち

起動時のセッション確認が終わるまで、全画面が読み込み中になる。

- 見つけ方: 起動直後の network で、セッション確認の完了まで他の描画と要求が止まっている
- 直し方の範囲: 認証が決まるまで後続の要求を出さないところまでは直してよい。署名付きの表示情報で先に描くは認証の設計を足す変更なので、次の条件を示して判断を仰ぐ
  - 表示情報のトークンは HttpOnly の Cookie に置き、JS に公開しない
  - 認証トークンのハッシュと有効期限に結び付け、サーバで両方の署名を検証する
  - 表示情報を認可の根拠にしない。API は最新の権限・失効を確かめ続ける
  - 401 で認証表示を終え、403 や通信障害ではログアウトさせない。遅れた古い応答で元の画面に戻らない
  - 個人別の HTML は `private, no-store` で返し、PWA などに保存しない

### 入口

入口から静的 import で辿れるコードが大きく、初回起動とメモリを重くする。

- 見つけ方: スキャナの「入口」（重いライブラリの静的 import）。入口ファイル（Worker / サーバのエントリ、ルーター）から API 全体や全 route を静的 import していないか。ビルド成果物で入口から辿れるファイルの合計を数える
- 確定の条件: 重いライブラリや API 本体が、それを使わない要求の入口から辿れる
- 直し方: 使うハンドラの中で動的 import する。route を要求された分だけ読み込む。起動直後に必ず呼ぶ API（セッション確認）は小さな入口へ分ける。動的 import を禁止する規約なら、例外の範囲と実測を ADR とコードコメントに書く
- 確かめ方: ビルド成果物の閉包サイズを前後で比べる。ビルド成果物を実行環境で起動して heap を測る。遅延読み込みの失敗は初回の要求で出るので、その経路をテストかデプロイ後の疎通確認で叩く

### 配信資産

初回に配る静的資産が大きい。

- 見つけ方: PWA の事前キャッシュの対象、CSS のフォント定義の数、ビルド成果物の大きいファイル
- 直し方: 事前キャッシュは起動に要る資産だけにし、遅延 chunk は使った後に保存する。同じ書体の太さ別の定義は可変フォントにまとめる
- 確かめ方: ビルドの前後で対象ファイル数とサイズを比べる。オフライン起動など既存の動作を実ブラウザで確かめる

### 無効化

速さのために持った画面側のキャッシュが、書き込みの後に古い集計を出し続ける。性能改善を入れるときに一緒に確かめる。

- 見つけ方: 集計を表示する query のキャッシュキーと、その集計に影響する書き込み（作成・訂正・承認・削除）の後の無効化処理を突き合わせる
- 直し方: 書き込みの成功後に、影響する集計のキーを無効化する
- 確かめ方: 書き込みの後、再読み込みせずに集計が更新されることを実ブラウザかテストで確かめる。保存に失敗したときは無効化しない

## 直さずに判断を仰ぐ視点

挙動・安全性・インフラに影響し、コードの同値性だけでは正しさを示せない。根拠（計測値・設定・代替案）を付けて、推奨案を 1 つ示す。

### 距離

計算（Worker・関数）と DB が遠く、往復ごとに待ち時間が増える。

- 根拠に付けるもの: 1 往復の待ち（SQL の実行時間と DB 呼び出しの経過時間の差）、計算の配置先（応答ヘッダ）、DB の地域
- 推奨の形: 主な DB の地域の近くへ配置を明示する。自動配置は反映後に配置先を確かめる。戻し方（設定を消す）を添える

### キャッシュ

段数・読み行数・計算を減らしても重い集計を、保存して先に表示する。

- 推奨の形: 認可と入力検証の後で読み書きする。キーに配信版・hostname・query・利用者・失効世代・権限の範囲・日付を入れる。期限を持ち、短い間は再集計を省き、それ以降は背景で更新する。画面に集計時刻と手動の更新を出す。HTTP キャッシュは `no-store`。環境ごとに保存先を分ける
- しない: 権限・失効の確認をキャッシュで省く

### 認可情報のトークン化

署名済みトークンに権限を載せ、検証だけで認可して前段の DB 読み取りを省く。

- 根拠に付けるもの: 前段の往復と読み行数、トークンの大きさ（Cookie の上限）
- 判断の論点: 権限の変更・停止・ログアウトが、トークンの有効期限まで反映されない。即時に反映するなら失効世代のような小さな値を 1 つ確かめる経路が残る。権限を変えたときの再発行
- 表示用の情報をトークンに載せる案でも、APIの最新の権限・失効の確認は省かない
