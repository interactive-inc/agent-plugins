# 手入れの対象

## code

対象の検証出力と呼び出し経路を確認し、重複・責務・型・配置のうち今回の目的を改善する。必要な点検は [check code](../../check/references/scopes.md#code) を参照する。

- 巨大ファイルは責務と依存で分ける。行数を移すだけの helper、クラス名だけのフォルダ、共有されない `types.ts` を増やさない。
- 配置と依存は [設計規約](../../dev/references/design/architecture.md) を正本とする。
- 内部整理は既存製品内で行う。再利用できるという理由だけで workspace・package・公開 API・独立 version を増やさない。独立した利用先と配布の必要がある場合は構成変更として相談する。
- 未使用候補は動的参照や公開入口まで確認する。試験を削るときは、対象機能が消えた等の理由を示し、期待値を実装へ合わせて不具合を隠さない。

移動・分割後は import / export と利用箇所の欠落・重複、CI・deploy の対象、変更した責務の試験を確認する。機能や意味の変更が必要なら、今回の手入れと区別して判断する。

## docs

[文書点検](../../check/references/scopes.md#docs) で確認した差から、現状の説明と実装を同期する。未反映の決定・将来の要件を、実装と違うだけで消さない。

完了済み backlog、日程、役目を終えた一時メモも確認し、経緯や人の記述を保ちながら整理する。[文書の整合規約](../../dev/references/docs/validation.md) に従い、関連する入口とリンクまで更新する。

## readme

README は人の入口、AGENTS.md / CLAUDE.md は agent が必要とする規約と制約に絞る。実装から自明な説明・重複は削り、意思決定の経緯は既存の `.docs/decisions/` などへ寄せる。同じルールを複製しない。

コマンドや参照先の実在を確認して部分更新し、人が書いた背景や保護された節を保持する。README を新しく作る仕事は [docs readme](../../docs/commands/readme.md)。
