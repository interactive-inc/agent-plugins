# 依頼を開発へつなぐ

自然文は目的から読む。観察された声は `signals/`、まだ判断する提案は `backlogs/`、合意した実装は対象製品の仕事として扱う。分類のために会話を止めず、記録や外部操作の結果が変わる場合だけ確かめる。

Issue番号・PR・URL・既存文書が示されたら、その本文と現在の実装を読み、続きとして進める。新しい記録を作る前に既存の関連記録を確認する。

## 対話と実装

目的・利用者・規模・期限・運用と失敗時の影響を会話からつかむ。未決定で作り方が変わる点を、推奨案と理由とともに問いかける。合意した範囲は実装と試験を進め、発見を全体へ戻す。詳しい共通の約束は [dev](../SKILL.md) を正本とする。

対話で得た背景と判断は [記録・整理](docs/development-context.md) に従って残す。声と未決の案は [signals](docs/signals.md)・[backlogs](docs/backlogs.md)、決定の理由は [decisions](docs/decisions.md) の書式を使う。利用者の記述は保護する。

## GitHubと作業場所

- 外部への記録・送信・公開は依頼された範囲で行う。操作は [GitHub](tools/github.md)、書式と属性は [Issue・PR](tools/issue-pr.md) を使う。
- 実装済みの計画や既存PRが今回の目的に合えば続きを使う。別の目的や複数の候補があるときは確認する。
- 製品の作業場所の規約を優先し、他者の変更・作業場所・保存済みの作業を上書きしない。主作業場所のブランチを切り替えて作業を混ぜない。
- Issue用の分離した作業場所を自分で作る場合は [初期化規約](guides/environment/worktree.md) に従う。既にその作業場所にいる場合は重ねて作らない。
- 同時に進める実装の範囲を確定し、共通基盤や同じ機能を別方向へ変更しない。

## 完了

実装と同時に守る動作を確かめ、[inta:test](../../test/SKILL.md) の該当する方法で検証する。文書の関係箇所を整理し、依頼された到達点まで進める。確認できたこと、未確認、方針と実装の食い違いを短く報告する。
