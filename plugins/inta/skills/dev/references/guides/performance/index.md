# 性能改善

指定されたコード・画面・API・差分の性能を、振る舞いを保って改善する。範囲がなければ、取得できる統計と共通の処理経路から影響の大きい候補を選ぶ。

## 進め方

1. 対象範囲と現在の試験を確認し、応答の直列待ち・DB の読み行数・CPU・転送・初回起動のどこに費用があるか調べる。[候補スキャナ](scripts/find-candidates.sh) は検索補助であり、結果をそのまま不具合としない。
2. [改善の観点](checks.md) から該当する部分を読み、計画・呼び出し回数・取得量などの根拠で候補を絞る。利用者への影響と費用の大きさで優先する。
3. 成功結果・認可・失敗後の状態を試験で固定してから修正する。[検証](verify.md) に従い、同じ条件で比較する。

## 判断の境界

- 速さのために認可・失効確認を省かない。本番 DB の調査は読み取り専用とし、変更は migration / deploy の正規経路を使う。
- 索引・述語・統計依存の実行計画は、影響する他のクエリと本番相当のデータで比較する。根拠が不足する変更は提案に留める。
- 配置・キャッシュ・認証方式・公開契約の変更は、今回の目的と許可範囲に含まれるかを先に判断する。
- 計測ログに秘密値・個人情報・SQL の bind 値を残さない。

結果には変更と根拠、同値の検証、比較条件、未確認・保留を示す。ローカルの SQL や呼び出し回数の改善を、配信後の画面速度として報告しない。

Cloudflare Workers + D1 の固有調査は [cloudflare-d1.md](cloudflare-d1.md)、説明用の架空例は [cases.md](cases.md)。画面速度の比較は [test perf](../../../../test/commands/perf.md)。
