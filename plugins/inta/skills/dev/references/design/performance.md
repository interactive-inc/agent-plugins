# Performance Design

サーバレス + リモート DB（Cloudflare Workers + D1 など）の製品で、応答時間を決めるのは DB の実行時間ではなく「直列の往復段数 × 1 往復の待ち」である。遅くなったときは、まずこの式のどの項が育ったかを疑う。

## 観点

変更の設計時と、本番が遅いと言われたときの両方で見る。兆候 → 疑う場所。

- CPU 時間に対して応答時間が桁違いに大きい → 待ちが支配的。DB 往復の段数と 1 往復の待ちを数える
- リクエストあたりの DB クエリ数が増え続けている → 認証・権限解決など全 API 共通の前段が肥大している。移行期の二重解決や一致検査はここに入りやすい
- 同じ SELECT が 1 リクエストで複数回走る → resource ごとに同じ行集合を取り直している。1 回読んでメモリで解く
- 静的なページでも散発的に数秒かかる → isolate 初回のモジュール読み込み。SSR 入口チャンクに API 全体やアイコン全量が同居していないか
- 保存 1 回で行数ぶんの UPDATE が走る → 1 行 1 往復。batch で 1 往復にする
- 利用が増えるほど特定画面だけ遅くなる → 毎回のフル再計算、全件取得して JS で絞る、`substr()` など式で絞ってインデックスが効かない条件
- クエリ単体が遅い（数百 ms〜） → ここで初めてインデックス欠落を疑う。WHERE / JOIN 列に対して索引の有無を突き合わせる

## 採用ルール

- 1 リクエストの DB 往復は段数で予算を持つ。認証・権限の前段は 2 段以内、ハンドラ本体は互いに依存しないクエリを同じ段に置く
- 互いの結果に依存しないクエリは `batch` で 1 往復にまとめる。Promise.all による並列は往復数を減らさないので、段を減らす手段としては batch を優先する
- 全 API 共通の前段にクエリを足すときは、往復数/リクエストへの影響を変更の説明に書く
- 締め済み・確定済みのデータはスナップショットを正として再計算しない
- 日付・月で絞る条件は範囲条件（`>=` と `<`）で書き、列に式をかけない
- インデックスは計測で必要になった列にだけ足す。予防的に足さない
- SSR の入口チャンクに API 本体を静的 import しない。バンドルの肥大は isolate 初回の待ちとして利用者に出る

## 判断の順序

1. 応答時間と CPU 時間の分布（P50 / P99）を取り、待ちが支配的かを確かめる
2. リクエストあたりのクエリ数と、クエリ別の実行回数・平均行数を取り、毎リクエスト走るものを特定する
3. 直列の段数を数え、段を減らす設計に直す
4. それでも遅いクエリが残るときだけインデックスと集計の見直しに進む
