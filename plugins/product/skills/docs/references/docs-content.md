# 顧客向け表現ルール

`.docs/` の内部表現を顧客向け HTML に移すときの判断基準。例示の製品固有語は、その製品の用語へ読み替える。

## 言い換え

| 内部表現 | 顧客向け |
|---|---|
| ペルソナと痛み | ご利用の方々 |
| 困っていたこと | 従来の状況 |
| 片付けたい仕事 | この役割の仕事 |
| 製品で変わること | 製品で実現できること |
| やらないこと | 対象範囲 |
| 商談時の注意 | （削除） |
| 残課題 | 公開済みroadmapなら「今後の対応」。内部backlogなら掲載しない |
| 制限: 〜次フェーズ | 現在の対象範囲と提供予定を、確認できた事実だけで説明 |
| 未実装 / 現状はモック | 提供状況を誤認させない平易な説明 |
| ロール | 役割 |
| 経営者ロール | 経営者 |
| API / ミドルウェア / DB / mutation | （削除または平易な言い換え） |
| auditLogs テーブル | 履歴データ |
| /audit-logs 画面 | 監査ログ画面 |
| JTBD | ユーザーが片付けたい仕事 |
| OOUI | （削除、説明だけ残す） |
| LLM | （削除、または「AI」） |
| DiffBadge | 差分バッジ |
| 出自: | 補足: |

## 外部成果物から除く内部情報

以下のセクション・パラグラフはまるごと削除する。

- 「商談時の注意（未実装）」セクション
- 営業・開発チームだけに向けた検討メモ
- 利用者の判断に影響しない実装途中の作業メモ
- 用語集の実装ジャーゴン項目（JTBD・OOUI・DiffBadge など）

## 残してよい専門用語

読者が業務上必要とする専門用語は、初出時に短く解説して残す。対象製品のglossaryを正本にし、次の型で書く。

- 略語（正式名称、製品内での意味）
- 業界用語（初見の読者が判断できる一文）
- 製品固有語（何を指し、どこで使うか）

## 機能カードの書き方

- 概要は2〜3行。「この画面で何ができるか」を主語に置く
- 「主な機能」リストは4〜7項目。動詞ベース（「〜を一覧表示」「〜を編集」「〜を自動計算」）
- カード右上に slug を `<span class="font-mono text-xs text-sub">` で添える（ID ラベルとして許容）
- 利用判断に影響する制限は、否定的な印象の回避より正確さを優先し、対象範囲として短く明示する
- 機能カード内に内部の URL パスやテーブル名は出さない

## 隠してはいけない情報

- 現在利用できない機能を利用可能と読める表現にしない
- 利用者の業務、権限、データ、安全性に影響する制限を削除しない
- roadmapと現在提供中の機能を混同しない
- 不確かな内容はコードまたは製品オーナーへ戻し、推測で埋めない
